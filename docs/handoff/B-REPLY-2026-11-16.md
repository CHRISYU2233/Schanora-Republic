## 2. 角标口径：选「B 降级」，但有一件与模型无关的必修项

### 2.1 这不是一个二选一

| 问题 | 根因 | 与模型的关系 |
|---|---|---|
| `knowledgeReferences` 恒回第 0 块（答案说第 14 节，引用指第 0 块） | **网关回填代码**：把固定的一条塞进引用列表 | **无关**。换 7b/70b 也修不了 |

### 2.2 B 降级已是现状（不用改代码）

前端本来就按「可能没有角标」设计：

- 无角标时：引用列表照常显示在答案下方，校验徽标显示「无角标」，用户能看到出处只是不能点跳；
- 有 `<kb/>` 标签时：渲染前自动转成 `[n]`（`lib/cite.js#normalizeCitations`，13 条单测，用你们 09:07 那条真实答案回放验证过）；
- 任何情况下都不会把裸标签直接显示给用户。

所以「B 降级」不需要 A 等 B 做什么——**已经是这个样子了**。

### 2.3 必修项：按本轮召回回填引用列表

把「本轮实际参与合成的命中块」按 score 降序写进 `knowledgeReferences`，替换现在固定第 0 块的逻辑。
检索接口字段是齐的（`id` 即分块 id、`chunkIndex`、`score`），这是确定性代码，与模型无关。

改完后即便模型一个标记都不输出，用户点引用列表也能看到**真正的来源块**，而不是永远第 1 块。

## 3. M6 Wiki：调研结果（回答你们的三个问题）

### 3.1 Wiki 是否独立于文档知识库

**不独立**。所有 Wiki 路由挂在 `/api/v1/knowledgebase/:kb_id/wiki` 之下
（上游源码 `internal/router/routes_knowledge.go`），且 Wiki 页面会**同步为 chunks 参与检索**。
读写都受 RBAC 约束：读要 `Viewer + KBAccessRead`，写要 `OwnedWikiKBOrAdmin + KBAccessWrite`。

### 3.2 tree / pages 怎么取

上游没有现成的单一 tree 端点，有两种组法：

| 方案 | 上游端点 | 说明 |
|---|---|---|
| A | `GET /folders` + `GET /pages` | 目录树 + 页面列表（支持 `page_type/status/query/folder_id/page/page_size/sort` 过滤分页） |
| B（推荐先试） | `GET /index` | `GetIndexView` 返回 `{intro, groups}` 结构化目录，按类型分组，最接近我们 tree 的形态 |

单页：`GET /pages/*slug`（通配符路由，slug 含路径分隔符也能取）。

### 3.3 有无编辑 / 版本 / 同步逻辑

**全都有**，比我们要的多：

- CRUD：`POST/PUT/DELETE /pages`、`/pages/*slug`、`/folders/:folder_id`、`PUT /move-page`；
- 版本：`GET /revisions/*slug`（带 `?version=N` 取该版本全文）、`POST /revert` 回滚；
- 版本号语义：`version` **只在用户可见字段**（title/content/summary/page_type/status）变化时 +1，
  纯簿记写入不升版本（`UpdatePageMeta` / `UpdateAutoLinkedContent`）——这个语义很好，网关透传即可；
- 仓库层 `Update` 带乐观锁；
- 链接图：`GET /graph`（全局 / ego 视图）、`POST /rebuild-links`、InLinks/OutLinks；
- 质量检查：`GET /lint/issues`、`POST /auto-fix`。

我们 M6 第一版只用**读**（tree + 单页），写接口不用暴露。

### 3.4 网关侧要处理的 4 个差异点

1. **路径风格**：上游是 `/knowledgebase/:kb_id/wiki`（单数 + 下划线），我们的契约是
   `/knowledge-bases/{kbId}/wiki`（复数 + 连字符）——网关做路径改写，B 侧不动；
2. **信封**：上游 Wiki 这组响应**多为裸对象**（不带 `{code,data}` 包装），网关需要包成统一信封；
3. **枚举值**：我们契约里 `type: topic|entity|hub`、`status: published|draft` 是占位，
   请 A 核对上游 `page_type`/`status` 的实际取值后回来对口径——B 侧 `normalizeWikiPage`
   对缺省值有兜底（`topic`/`published`），但字典文案要按真实枚举更新；
4. **sources[]**：上游 `SourceRefs` 文档描述为 `|` 分隔的字符串，且另有 `ChunkRefs` 分块级引用；
   我们契约里 `sources[]` 是 `{knowledgeId, title, chunkCount}` 对象数组，需要网关解析拼装。

### 3.5 B 侧限制提醒

Wiki 正文渲染目前只支持**段落 / 列表 / 粗体 / 行内代码**（`RichText`）。
上游若返回表格、图片，第一版会降级为纯文本显示。如果你们的 Wiki 页面大量用表格，
说一声，B 再扩渲染器。

### 3.6 三项口径已定（2026-11-16 下午，B 侧拍板）

§3.4 里留给你们核对的三个点，B 侧现在直接定掉，A 照此实现即可：

1. **type / status 枚举：透传上游原生取值**，不做语义映射。契约里的 `topic|entity|hub` 等占位作废；
   A 只需回告一份上游 `page_type` / `status` 的实际取值清单，B 更新字典文案即可，代码有兜底。
2. **tree 主用 `/index`**（`{intro, groups}` 结构化目录，单请求）；不够用再由网关在服务端回退
   `/folders + /pages` 拼装。对 B 暴露的端点不变，仍是 `/knowledge-bases/{kbId}/wiki/tree`。
3. **sourceRefs 格式说明：要**，已写进契约（`C-PLUGIN-PORT.md` 五章「已定口径」第 3 条）：
   `|` 分隔 → 文档级 `sources[]`，解析失败的项丢弃并记日志，`ChunkRefs` 第一版不暴露。

```

# 防火墙：允许入站 TCP 8000（公用+专用配置档都放）
```
