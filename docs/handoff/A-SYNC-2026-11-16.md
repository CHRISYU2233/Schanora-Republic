## 3. A-1（P0）合成答案无引用标记 + 引用列表恒指第 0 块

### 3.1 现象

本次深度研究共 4 次问答，答案正文 **`[n]` 0 处、`<kb/>` 0 处**；`knowledgeReferences` 每条都是 **1 条**，
且 `chunkIndex` 恒为 `0`。而答案实际引用的是文档第 5 / 14 / 17 节。

用户侧后果：答案看着正常，但**点角标只能跳到文档开头**，等于「有出处列表、无法回指原文」。

### 3.2 关键证据：不是前端渲染问题

同一会话 `92102a61-1611-483a-bb31-d9b48d824a87`（`联调自测会话`）的助手消息时间线：

| 时间 | 长度 | `<kb/>` 标签 | `[n]` | refs |
|---|---|---|---|---|
| 09:06:44 | 180 | **1** | 0 | 1 |
| 09:07:27 | 429 | **2** | 0 | 1 |
| 10:44:58 | 298 | **0** | 0 | 1 |
| 10:46:41 | 301 | **0** | 0 | 1 |
| 10:50:40 | 114 | **0** | 0 | 1 |
| 10:51:19 | 316 | **0** | 0 | 1 |

09:07 那条引用的是 `.tmp_test_doc.md`——该文件名不在 B 侧上传记录里（B 侧上传一律命名为
`联调文档-<时间戳>.md`），应为 A 侧自测文档。原文含：

```
…住宿费一晚最多可以报销500元。<kb doc=".tmp_test_doc.md" chunk_id="fc791c69-92ec-47e7-b7fc-2c1ff841a837" kb_id="9d56b682-0307-4d8e-9584-e13984572355" />
```

→ **上游曾经输出过引用标签，10:44 之后不再输出**。差异出现在 A 侧合成链路（prompt / 模型 / 后处理），
不在 B 侧渲染。建议对照 09:07–10:44 之间对 `routers/qa.py` 与合成 prompt 的改动。

### 3.3 引用列表与答案不对齐的硬证据

10:51:19 那条答案说「这是在**第 14 节**中明确提到的」，而 `knowledgeReferences[0]` 是：

```json
{ "id": "49487195-1538-47d6-92ae-4303ff4f2c57", "knowledgeTitle": "联调文档-20261116024605.md", "chunkIndex": 0 }
```

该 `id` 在分块接口里正是 **第 0 块**：

```bash
GET /api/v1/documents/1d625a0f-c6db-414b-acd7-3ce6d713239d/chunks?page=1&page_size=2
# items[0] => { "id": "49487195-1538-47d6-92ae-4303ff4f2c57", "chunkIndex": 0, "startAt": 0, "endAt": 337, ... }
```

即：**引用列表固定回填文档首块**，与答案实际依据的块无关。

### 3.4 建议改法（二选一，建议都做）

**改法 ①：让合成答案带标记（治本）**

在合成 prompt 中加硬约束，并明确标记口径：

```
回答中的每个事实句后必须标注来源，格式 [n]；
n 是该事实所依据的召回块在“参考块列表”中的序号（从 1 开始）。
不得编造未出现在参考块列表中的序号。无依据时直接说明资料不足。
```

**改法 ②：按本轮召回回填 `knowledgeReferences`（兜底，且必须做）**

现在固定取第 0 块。应改为：把本轮实际参与合成的命中块按 `score` 降序写入
`knowledgeReferences`，顺序与答案里的 `[n]` 一一对应。检索接口已经给足了字段：

```jsonc
// POST /api/v1/search 返回的 item（实测字段）
{ "id": "<chunkId>", "chunkIndex": 9, "knowledgeTitle": "…", "knowledgeId": "<docId>",
  "score": 0.5693, "startAt": 2545, "endAt": 2862, "matchType": 0, ... }
```

`id` 即分块 id，`chunkIndex` 与 `GET /documents/{id}/chunks` 的 `chunkIndex` 同源，可直接用于角标定位。

**注意**：SSE 的 `references` 事件目前在 `answer` 之前发出（顺序正确，无需调整）；
只需保证该事件里的数组就是最终答案引用的那几块、且顺序稳定。

### 3.5 B 侧已就绪，A 给标记即可显示

B 侧已实现 `<kb …/>` → `[n]` 的适配：按 `chunk_id` 匹配 `knowledgeReferences` 得到序号，
对不上就删标签、不编造落不回列表的出处（`src/lib/cite.js#normalizeCitations`，13 条单测）。
用 A 的历史答案回放验证过：`…住宿费一晚最多可以报销500元。 [1]`，裸标签 0 处。

**标签口径**（两种都支持，任选）：

- `[n]`：`n` 必须等于该块在 `knowledgeReferences` 中的下标 + 1；
- `<kb doc="…" chunk_id="…" kb_id="…" />`：`chunk_id` 必须能在 `knowledgeReferences[].id` 中找到。

## 4. A-2（P1）ClipService 四端点未实现

实测（2026-11-16 11:0x 复测，四次均 404）：

```bash
POST /api/v1/clips                        -> 404
POST /api/v1/clips/{id}/commit            -> 404
GET  /api/v1/clips/{id}                   -> 404
GET  /api/v1/jobs/{jobId}                 -> 404
```

**判定为「路由未注册」而非「资源不存在」**——响应体与随机路径完全一致：

```jsonc
// POST /api/v1/clips          （空 body）
{"code":"NOT_FOUND","message":"Not Found","data":null,"retryable":false,"requestId":"afea1b3e6782"}
// GET /api/v1/zzz-nope        （对照：随机不存在路径）
{"code":"NOT_FOUND","message":"Not Found","data":null,"retryable":false,"requestId":"d7f5c87884e1"}
```

两者一字不差，说明是网关全局 404 兜底，四个路由都还没挂。若将来接口已注册但候选不存在，
请返回 `404 CLIP_NOT_FOUND`（带 `message` 区分），B 侧会把它当业务态而不是「未实现」。

影响：P1「网页剪藏 / 工程速记」的真实入库链路（含 OneDrive → WeKnora）无法验收，验收表 T04 仍挂 `mock_only`。
B 侧界面、去重键、版本裁决、状态机均已实现并有 18 条单测，**只差这四个端点**。

合同已在仓库：**`docs/handoff/D-CLIP-SERVICE.md`**（v0.1，提案态）。最小可用实现顺序建议：

1. `POST /api/v1/clips` → 落候选（`status=previewReady`），返回 `id/revision/dedupeKey`，缺 `targetKbId` 回 `400 SCOPE_REQUIRED`；
2. `POST /api/v1/clips/{id}/commit` → 校验 `expectedRevision`（冲突 `409 REVISION_CONFLICT`），按 `idempotencyKey` 幂等，返回 `queued` + `jobId`；
3. `GET /api/v1/jobs/{jobId}` → `queued|processing|ready|failed` + `documentId`；
4. `GET /api/v1/clips/{id}` → 出参同 1，供刷新后恢复。

版本语义（T05/T06 的判据）：同 `sourceKey` + 同 `contentHash` → `reuse`；同 `sourceKey` + 异 `contentHash` → `new_version`（`documentId` 不变）；无记录 → `create`。
