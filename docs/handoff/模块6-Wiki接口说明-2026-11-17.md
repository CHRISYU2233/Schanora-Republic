# 模块 6 · Wiki 接口说明

> 2026-11-17 · A（后端）给 B（前端）
> 契约正文在 `docs/api.md` **§6**，这里只列容易踩的点。

## 一、两个端点

```http
GET /api/v1/knowledge-bases/{kbId}/wiki/tree           # 目录
GET /api/v1/knowledge-bases/{kbId}/wiki/pages/{slug}   # 单页（多一个 content）
```

`{slug}` 含 `/`，形状是 `concept/部署方式`、`summary/<uuid>` 这类，路由按 `{slug:path}` 匹配。

## 二、字段口径

```json
{
  "slug": "concept/部署方式",
  "title": "部署方式",
  "type": "topic",
  "pageType": "concept",
  "status": "draft",
  "summary": "",
  "version": 1,
  "updatedAt": "2026-11-17T03:20:11Z",
  "sources": [{ "knowledgeId": "e6af2c66-…", "title": "", "chunkCount": 2 }]
}
```

| 字段 | 说明 |
|---|---|
| `type` | **只会是 `topic` / `entity` / `hub` 三种**，分组用这个 |
| `pageType` | 上游原始类型（`summary`/`concept`/`entity`/`index`/`synthesis`/`comparison`），仅供排查，不用渲染 |
| `status` | `draft` / `published` |
| `sources[].title` | **恒为空串**，上游不提供 |
| `sources[].chunkCount` | 该来源的分块数；回填失败时为 `0` |

`type` 的归类口径（上游 6 种 → 对外 3 种）：

| 上游 `pageType` | 对外 `type` |
|---|---|
| `concept` / `synthesis` / `comparison` | `topic` |
| `summary` / `index` | `hub` |
| `entity` | `entity` |
| 其它 / 空 | `topic` |

> ⚠️ 别用 slug 前缀判断类型。实测有 `slug=concept/xxx` 但 `pageType=entity` 的页面。

## 三、错误场景

| 场景 | HTTP | `code` |
|---|---|---|
| 知识库未开 Wiki | 400 | `BAD_REQUEST` |
| 知识库不存在 | 404 | `NOT_FOUND` |
| slug 不存在 | 404 | `NOT_FOUND` |
| 上游不可达 / 超时 | 502 / 504 | `UPSTREAM_ERROR` / `UPSTREAM_TIMEOUT` |

- `code` 是**字符串**，不是数字（旧版 `api.md` §0.2 写的是数字码，已更正）。
- 判断可重试看 `retryable` 字段，不要枚举状态码。
- **wiki 开了但还没有页面时返回 `200` + `items: []`**，不是 400 也不是 404。
- 每个响应（成功和失败）都有 `X-Request-Id` 头，你传进来会原样透传。

## 四、四个会被当成 bug 的正常行为

| 现象 | 原因 | 处理 |
|---|---|---|
| `sources[].title` 是空串 | 上游 `source_refs` 只给 `knowledgeId` | 用 `knowledgeId` 反查文档名，或留空 |
| `status` 全是 `draft` | 自动生成的页面默认草稿态 | 别只渲染 `published`，否则列表是空的 |
| 页面数量自己会变多 | 上游 ingest 分多轮跑，一份文档从 3 页涨到 15 页 | 列表给个刷新入口 |
| `items: []` | wiki 已开但还没生成出页面 | 显示空态，不要当错误 |

## 五、待确认：`type` 是归一化还是透传

两处约定不一致，需要你确认一次：

- `C-PLUGIN-PORT.md` §五 定的是 `type: topic | entity | hub`（三值）
- `A-TODO-R3.md` P1-2 写的是「透传上游原生值，不做语义映射（B 侧字典会跟上）」

当前接口按前者实现：返回 `topic | entity | hub`，上游原值另放在 `pageType`（见第二节映射表）。

两种走法：

| 方案 | 网关 | 前端 | 代价 |
|---|---|---|---|
| **A · 保持归一化（现状）** | 不改 | 不用改，现有的 `wiki.type.topic` / `entity` / `hub` 直接可用 | 上游 6 种细分只能从 `pageType` 读 |
| **B · 改回透传** | 改一处映射 | 要补 `summary` / `concept` / `index` / `synthesis` / `comparison` 五个文案键，分组逻辑也得跟着改 | 保留细分类型，工作量在前端 |

建议 A，理由三条：

1. 前端字典目前只有三个键，不改就能跑；
2. 上游 `page_type` 是它自己的内部实现，`synthesis` / `comparison` 在实际数据里出现很少，归到 `topic` 不影响浏览；
3. 真要细分，`pageType` 已经在每个 item 里，随时可以按需渲染，不用动接口。

回一句「A」或「B」即可。选 B 的话接口改动很小，但要等前端文案补完再切，否则中间态会显示裸 key。

```
kbId = d775979b-2c02-4bdd-914c-1f83a9154586

内容 = wiki 已开，15 页（entity 6 / topic 5 / hub 1，全部 draft）
```

`slug` 里的中文按段编码即可（`encodeURIComponent` 保留 `/`），原样中文也能请求。
